# FINDINGS.md — Part A triage

Read: `ASSIGNMENT.md`, `RUNBOOK.md`, every tracked file, and `git log -p` on
`main` (all 12 commits). Data is synthetic but ranked as if it were real
patient health data, per the brief.

Severity: **critical** (data breach / patient-safety / total compromise, low
effort to trigger) · **high** (serious but needs one more condition, or
degrades safety/reliability badly) · **medium** · **low**.

Status: **fixed** (the code in this repo fixes it) · **guardrailed** (a real
control reduces the risk but doesn't fully close it, or needs a human step
to finish) · **documented-only** (known, written down, not acted on). A few
rows were fixed by leaving the old GCP box behind entirely, not by patching
it — those say "fixed (replatform)"; the old VM/project itself still needs
decommissioning, which stays documented-only.

1. SEC-01 — SQL injection in patient lookup

## Runtime & reliability bugs (code-level, not just config)

| ID | Title | Where | Why it matters | Severity | Status |
|---|---|---|---|---|---|
| APP-02 | Reminders are marked `sent` even when the send failed | `notifier/notifier.py`: `send_one` swallows the HTTP exception (`except Exception: print`) and `run_once` unconditionally runs `UPDATE reminders SET status='sent'` right after | For a medical reminder system this is silent data loss: a patient can miss an appointment because the send failed, and the DB says it went out. No retry, no dead-letter, no alert | critical | fixed — only marked `sent` after `send_one()` actually returns true; a failure leaves the row `queued` for the next run to retry, tested |
| APP-02b | notifier ignores `send_at` — every queued reminder goes out on the very next loop, not at its scheduled time | `notifier/notifier.py`: `fetch_queued`'s query has no `send_at <= now()` filter, only `WHERE r.status = 'queued' ORDER BY r.send_at LIMIT 50` | A reminder scheduled for 3 days from now is sent within the next 30-second loop tick instead. This is a patient-facing correctness bug, not just an ops risk — ranked together with APP-02 since both mean "the patient did not get what the system believes it sent" | critical | fixed — `fetch_due()` filters `send_at <= now()`, tested |
| APP-01 | Unhandled DB/query errors crash the whole portal process | `portal/src/index.js` — every route `await`s `pool.query` with no try/catch, no error middleware; Express 4 does not catch async-handler rejections, so it becomes an unhandled promise rejection | Any transient DB hiccup, malformed request, or a schema mismatch (see DATA-01) takes down the *entire* service, and `docker-compose.yml` has no `restart:` policy on `portal` — it stays down until someone notices manually | critical | fixed — every route wrapped, one error middleware returns 500 JSON instead of crashing; also now runs on Lambda with bounded concurrency, so one bad request can't take down every request either |
| APP-06 | Unhandled exception in `write_receipt` can crash the notifier after reminders are already marked sent | `notifier/notifier.py`: `write_receipt(rows)` call in `run_once` has no try/except, unlike `send_one`'s HTTP call | GCS auth/network failure kills the process mid-batch; the per-row `UPDATE ... status='sent'` + `commit()` already happened, so a crash here loses the receipt with no retry, while the reminders are already (possibly wrongly, see APP-02) marked sent | high | fixed — `write_receipt` wraps its S3 call, logs and continues on failure instead of crashing the run |
| APP-07 | notifier opens one DB connection for the life of the process, never reconnects | `notifier/notifier.py`: `main()` calls `psycopg2.connect(**DB)` once, outside the `while True` loop | Any DB restart or network blip after that point raises on the next query and is unhandled — the process dies and depends entirely on the 5-minute cron restart (`ops/CRONTAB.txt`) to come back, extending the reminder-delivery gap | medium | fixed — `main()`'s loop catches `OperationalError` and reconnects; prod now runs as a per-invocation Lambda (`handler()`) that opens a fresh connection every 15 minutes rather than one long-lived process |
| APP-03 | Unbounded in-memory list, never cleared | `notifier/notifier.py:29` (`sent_this_process`), appended every send in the infinite `while True` loop | Long-running process leaks memory indefinitely (holding email/DOB — PII — in RAM) until OOM-killed; comment literally says "Never cleared" | high | fixed — `sent_this_process` removed entirely, nothing accumulates across iterations |
| APP-04 | PHI written to plaintext logs | `notifier/notifier.py:44-48` (full name, email, DOB per send); `portal/src/index.js:9` (whole request body), `:31` (looked-up email) | Health-adjacent PII in stdout with no redaction, no access control, no retention policy — gets worse the moment any log shipping/observability is added | high | guardrailed — notifier logs reminder id/channel only now, never name/email/DOB; portal never logs the request body or looked-up email (only actor + result count). Error-level log lines are still free-text exception messages, not redaction-guaranteed against every possible driver error string |
| APP-10 | Receipts written to GCS contain full patient rows in plaintext, kept indefinitely | `notifier/notifier.py`: `write_receipt` uploads `json.dumps([list(r) for r in rows])` — includes `full_name`, `email`, `dob` per reminder | PHI at rest in object storage with no encryption-at-rest policy called out and no lifecycle/retention rule on the bucket — and per SEC-15, a misconfigured env can send it to the wrong (prod) bucket entirely | high | fixed — receipts now contain only reminder id/channel/status/timestamp, no PII; moved to S3 (private, SSE-S3, TLS-only, 90-day expiry) with no default bucket |

## Cut on purpose

What week one didn't do, and why:

- **SEC-13 (email in URL query string) stays documented-only.** Moving it to
  a POST body or a hashed lookup key is a real API change the care team's
  existing tooling would need to follow; not worth doing under time
  pressure without coordinating that.
- **No SSO/IAP for the portal.** Named app-level tokens get most of the
  accountability benefit for a fraction of the setup, for a handful of
  internal users. Real SSO is the right answer once there's an identity
  provider worth wiring up to — see README.
- **The uptime check runs inside AWS**, so a full-region outage is a blind
  spot (documented in `uptime/handler.py`). An external checker is a
  small, separate task, not a design change — cut for time, not
  difficulty.
- **The old GCP VM/project was never touched.** Everything it did has a
  replacement in the new architecture, but decommissioning the actual box,
  rotating the actual leaked key, and deleting the actual DNS record are
  manual steps in a console this repo has no access to.
- **GitHub Actions are pinned to major versions, not commit SHAs.**
  Deliberate first cut (documented in `ci.yml`) — SHA-pinning is a
  mechanical follow-up, not a design decision.
- **No dependency vulnerability scanning for app code** (npm audit /
  pip-audit equivalents) — only container images are scanned (trivy).
  Same shape of gap as the Actions pinning: real, small, not this week.
- **NEN 7513-grade audit logging wasn't built.** What exists (actor-tagged
  request logs) is a real improvement over "no attribution at all," not a
  compliant audit trail with retention and review built in.
